## 1. 브랜치

- `main`은 「어떤 상태로 두는가」. 「main에 직접 하지 않는 것」
- 이름은 `<종류>/<설명>`이다.
  - 종류: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`
  - 뒤의 장이 더하는 종류: `loop`(8장, 루프 실험. 예: `loop/success-1`), `practice`(8장, 연습), `agent`(10장, 에이전트 하나의 작업 브랜치 `agent/<이슈>-<작업>`. 예: `agent/issue-07-t1`). 10장에서 이슈 하나를 모으는 통합 브랜치는 `feat/issue-NN`이다. `check_commits.py --branch`는 처음부터 이 종류도 허용한다.
  - 설명: 「글자의 규칙」. 예: 「예 셋」

## 2. 커밋 메시지

Conventional Commits 1.0.0을 따른다.

```text
<종류>[(범위)][!]: <설명>

[본문]

[꼬리말]
```

| 종류 | 쓰는 경우 |
|---|---|
| `feat` | 「」 |
| `fix` | 「」 |
| `docs` | 「」 |
| `test` | 「」 |
| `refactor` | 「」 |
| `chore` | 「」 |
| `build` | 「」 |
| `ci` | 「」 |
| `revert` | 「」 |
| 「그 밖에 쓰는 종류」 | 「」 |

- 범위: 「이 저장소에서 쓰는 범위 목록」. 요구 하나를 다루는 커밋은 범위에 요구 ID를 쓴다(예: `feat(REQ-JOB-06): …`, 2장)
- 설명: 「언어, 마침표, 길이」
- 하위 호환을 깨는 변경: 「」
- 꼬리말: 「요구와 잇는 방법」

## 3. 풀 리퀘스트

- 「PR 하나의 크기와 목적」
- 「본문을 쓰는 방법」
- PR을 열기 전에 통과해야 하는 명령: 「셋」
- 병합 방식: 「」. 이유: 「」

- 「에이전트가 만든 변경의 리뷰 기준」
