# jobprep 저장소 규약

| 항목 | 내용 |
|---|---|
| 판 | v1.0 (3장) |
| 적용 범위 | 이 저장소에서 일하는 모든 사람과 에이전트(Claude Code, 이후 장의 역할 에이전트) |
| 함께 보는 파일 | `CLAUDE.md`(에이전트가 매 세션 읽는 요약), `.claude/settings.json`(권한), `.github/pull_request_template.md`, `CODEOWNERS` |
| 검사 도구 | `ops/rules/check_commits.py`(커밋 메시지, 브랜치 이름), `ops/rules/lint_rules.py`(규칙 파일) |

이 문서가 원본이다. `CLAUDE.md`에는 이 문서의 요점만 두고, 규약을 바꿀 때는 이 문서와 검사 도구를 함께 고친다.

## 1. 브랜치

- `main`은 언제나 테스트가 모두 통과하는 상태로 둔다. `main`에 직접 커밋하거나 푸시하지 않는다.
- 작업마다 `main`에서 새 브랜치를 만든다. 이름은 `<종류>/<설명>`이다.
  - 종류: `feat`, `fix`, `docs`, `test`, `refactor`, `chore`, `ci`
  - 뒤의 장이 더하는 종류: `loop`(8장, 루프 실험. 예: `loop/success-1`), `practice`(8장, 연습), `agent`(10장, 에이전트 하나의 작업 브랜치 `agent/<이슈>-<작업>`. 예: `agent/issue-07-t1`). 10장에서 이슈 하나를 모으는 통합 브랜치는 `feat/issue-NN`이다. `check_commits.py --branch`는 처음부터 이 종류도 허용한다.
  - 설명: 영문 소문자, 숫자, 하이픈. 예: `feat/closing-within`, `chore/team-rules`, `fix/ask-empty-question`
- 브랜치 하나는 목적 하나이다. 목적이 둘이면 브랜치와 PR을 나눈다.

## 2. 커밋 메시지

Conventional Commits 1.0.0을 따른다. 첫 줄의 형식은 다음과 같다.

```text
<종류>[(범위)][!]: <설명>

[본문: 무엇을 왜 바꾸었는가]

[꼬리말: Refs: REQ-JOB-06]
```

| 종류 | 쓰는 경우 |
|---|---|
| `feat` | 사용자에게 보이는 기능을 더한다 |
| `fix` | 결함을 고친다 |
| `docs` | 문서만 바꾼다 |
| `test` | 테스트만 더하거나 고친다 |
| `refactor` | 동작을 바꾸지 않고 구조를 고친다 |
| `perf` | 성능을 고친다 |
| `style` | 서식만 바꾼다 |
| `build` | 의존성, 패키지 설정을 바꾼다 |
| `ci` | 지속적 통합 설정을 바꾼다 |
| `chore` | 그 밖의 관리 작업(규칙 파일, 도구) |
| `revert` | 앞의 커밋을 되돌린다 |

- 범위는 선택이다. 이 저장소의 범위: `api`, `rag`, `web`, `tests`, `docs`, `ops`, `claude`(규칙과 설정 파일). 요구 하나를 시험하거나 구현하는 커밋은 범위에 요구 ID를 쓴다(예: `test(REQ-JOB-06): …`, `feat(REQ-JOB-06): …`, 2장).
- 설명은 한국어로 쓰고, 끝에 마침표를 찍지 않는다. 첫 줄은 72자 이하이다.
- 하위 호환을 깨는 변경(응답 형식의 키를 바꾸는 등)은 종류 뒤에 `!`를 붙이고 본문에 영향을 적는다.
- 요구와 관련된 커밋은 꼬리말에 `Refs: REQ-…`를 적는다.
- 2장의 원칙을 이어서, 테스트가 통과하는 단위로 커밋한다.
- 커밋 메시지는 `.githooks/commit-msg` 훅이 검사한다. 클론마다 한 번 `git config core.hooksPath .githooks`를 실행해 켠다. 에이전트는 `--no-verify`로 훅을 건너뛰지 않는다(팀 설정에서 거부).

## 3. 풀 리퀘스트

- PR 하나에는 브랜치 하나의 목적만 담는다. 바뀐 줄이 400줄을 넘으면 나누는 것을 먼저 검토한다.
- 본문은 PR 템플릿(`.github/pull_request_template.md`)의 항목을 모두 채운다.
- PR을 열기 전에 가상 환경을 켠 터미널에서 다음 세 명령이 모두 통과해야 한다.
  1. `python -m pytest -q`
  2. `python ops/rules/lint_rules.py`
  3. `python ops/rules/check_commits.py --range main..HEAD`
- 병합은 GitHub의 기본 방식(병합 커밋)으로 한다. 이유: 2장에서 테스트 통과마다 남긴 커밋을 그대로 보존한다.

## 4. 리뷰

- 모든 PR은 작성자가 아닌 사람 1명 이상의 승인을 받는다. 개인 저장소에서 혼자 일하는 동안에는 작성자가 PR 템플릿의 점검표로 자기 검토를 하고 기록을 남긴다.
- `CODEOWNERS`에 소유자가 있는 경로를 바꾸면 그 소유자의 검토를 받는다.
- 규칙 파일(`CLAUDE.md`, `.claude/`, `CODEOWNERS`, `.github/`, 이 문서)을 바꾸는 PR은 본문의 "규칙 파일 변경" 칸에 무엇을 왜 바꾸었는지와, 바꾼 뒤 `lint_rules.py`의 결과를 적는다.
- 에이전트가 만든 변경도 사람이 만든 변경과 같은 기준으로 리뷰한다. 에이전트의 완료 보고가 아니라 diff와 검사 결과를 본다.

## 5. 개인 설정

- `.claude/settings.local.json`과 `CLAUDE.local.md`는 저장소에 올리지 않는다(`.gitignore`에 있다).
- 개인 설정에는 개인 취향과 이 컴퓨터에서만 맞는 값만 둔다. 팀원 모두에게 필요한 허용 규칙이나 지시는 PR로 팀 파일에 올린다.
