# jobprep 하네스 설계서 (7장 기준 산출물 견본)

> 7장 키트의 `기준산출물/`과 `조립/`로 조립한 하네스 v1을 기준으로 채운 견본이다(7장 키트 `교수/하네스설계서_견본.md`의 사본). 7장을 마치지 못한 학습자가 8장부터 쓴다. 자기 설계서가 있으면 그것을 쓴다.

## 1. 개요

| 항목 | 내용 |
|---|---|
| 하네스 이름과 판 | jobprep-harness v1 |
| 적용 저장소와 기준 태그 | `jobprep`, 태그 `harness-v1` |
| 작성자, 날짜 | (학습자), 2027-11-(수업일) |
| Claude Code 버전과 모델 | 2.1.296(집필 시점), 측정 모델 haiku |

## 2. 목표

jobprep 저장소에서 에이전트가 기능 구현, 운영 문서, 운영 코드를 맡을 때, 테스트 회피, 명세 누락, 비밀 정보 노출, 사용자 입력의 기록, 근거 없는 보고가 일어나지 않게 한다.

## 3. 범위

- 대상 작업: 기능 구현(API), 운영 문서(장애 보고서), 운영 코드(기록)
- 실행 방식: 대화형과 헤드리스 모두. 헤드리스에서는 `--bare`를 쓰지 않는다(쓰면 훅, `CLAUDE.md`, MCP, 플러그인이 빠진다)
- 하지 않을 것:
  1. 사람의 병합 승인과 배포 결정을 대신하지 않는다(13장).
  2. 취향(이름 짓기, 문체)은 강제하지 않는다. 강제는 예외가 없는 규칙에만 쓴다.
  3. 실제 키를 다루는 작업(키 교체, 키 확인)은 자동화하지 않는다.

## 4. 관찰한 실패와 근거

| 번호 | 관찰한 실패 | 근거 | 피해 |
|---|---|---|---|
| F1 | 동결된 테스트 파일을 고쳐 테스트를 통과시킴 | 2장 테스트 동결 검사, 하네스비교 T1-off | 완료 조건이 무너진다 |
| F2 | 기능을 바꾸고 명세서를 고치지 않음 | 3장 규칙비교, 하네스비교 T1·T3-off | 명세와 코드가 갈라진다 |
| F3 | 인증 오류를 조사하며 `.env`를 읽음 | 하네스비교 T2-off | 키가 대화 기록과 서버 밖으로 나간다 |
| F4 | 보고서에 기록에 없는 원인을 사실처럼 씀, 복구 시각을 다른 기능의 성공으로 정함 | 4장 스킬비교, 하네스비교 T2-off | 잘못된 대책 |
| F5 | 기록에 질문 원문을 남김 | 하네스비교 T3-off | 개인 정보가 기록에 쌓인다 |
| F6 | 구현한 쪽이 자기 변경을 검토해 빠진 요구를 놓침 | 6장 검토자검증 | 결함이 병합된다 |

## 6. 하네스 요구 (EARS)

| 번호 | 요구 | 부품 | 검증 방법 |
|---|---|---|---|
| H1 | 만약 에이전트가 동결된 테스트 파일을 고치려 하면, 하네스는 그 편집을 막고 까닭을 알려야 한다. | P4 | `check_hooks.sh`의 `pre_edit_frozen_test` 사례 |
| H2 | 만약 에이전트가 `.env`를 읽으려 하면, 하네스는 그 호출을 거부해야 한다. | P3 | 실행 기록의 `permission_denials`, `.env` 노출 0 |
| H3 | 에이전트가 응답을 끝내려 할 때 전체 테스트가 실패하면, 하네스는 한 번 되돌려 보내야 한다. | P6 | `check_hooks.sh`의 `stop` 사례 |
| H4 | 하네스는 헤드리스 실행에서도 대화형과 같은 훅과 규칙을 적용해야 한다. | P1~P6 | `harness_check.sh`의 「공유 설정에 Stop 훅」 |
| H5 | 에이전트가 장애 보고서를 쓸 때, 하네스는 기록 요약 도구와 보고서 서식, 서식 검사를 제공해야 한다. | P7, P8 | T2 보고서 검사 10항목 |

## 7. 공유와 배치

| 부품 | 둘 곳 | 까닭 |
|---|---|---|
| P1, P2, P3 | 저장소 | 이 저장소의 명령과 규칙이다. 플러그인에 넣을 수 없다(플러그인의 CLAUDE.md는 실리지 않고, 권한은 플러그인 구성 요소가 아니다) |
| P4~P6, P9 | 저장소 + 플러그인 `jobprep-harness` | 같은 구조의 다른 저장소에서도 쓴다. 한 저장소에서 둘을 함께 켜지 않는다(훅이 두 번 돈다) |
| P7 | 플러그인 `jobprep-ops` | 4장에서 묶었다 |
| P8 | 저장소 | 서버 코드가 이 저장소의 기록 형식에 묶여 있다 |
| 개인 선호 | `settings.local.json`, `CLAUDE.local.md` | 팀에 강제할 것이 아니다 |

## 8. 충돌과 해결

| 번호 | 부딪친 것 | 종류 | 해결 | 까닭 |
|---|---|---|---|---|
| C1 | 6장의 Stop 훅이 개인 설정(`settings.local.json`)에만 있음 ↔ 하네스를 팀과 실험 저장소에 같게 적용 | 배치 | Stop 훅을 공유 설정으로 옮김 | 개인 설정은 복제·실험 저장소에 따라가지 않는다(gitignore) |
| C2 | CLAUDE.md 「구현을 고친 뒤 관련 테스트를 돌린다」 ↔ PostToolUse·Stop 훅 | 지시와 강제의 중복 | CLAUDE.md에는 「보고에 결과를 붙인다」만 남김 | 같은 일을 두 곳에 두면 한쪽을 고칠 때 다른 쪽이 낡는다 |
| C3 | 검토자 규칙 RV1~RV6 ↔ 설계서의 실패 F2, F5 | 부품과 실패 목록의 불일치 | RV7(기록의 사용자 입력), RV8(명세 동기화)을 더함 | 실패 목록에 있는데 어느 부품도 감지하지 않는 실패가 있었다 |
| C4 | 편집 뒤 테스트 훅의 시간 | 훅의 비용 | 관련 테스트만 돌리는 6장 방식을 유지, 전체 테스트는 Stop에서 한 번 | 편집 6회 × 관련 테스트 + Stop 1회. 측정값은 비교표에 적는다 |

## 9. 측정 계획

| 항목 | 내용 |
|---|---|
| 가설 | on에서 규칙 위반과 `.env` 노출이 줄고 인수 통과율이 오른다. 토큰과 시간은 늘어난다 |
| 작업 | T1, T2, T3 |
| 조건 | off(하네스 부품 삭제), on(harness-v1). 같은 모델(haiku), `run_task.sh`의 같은 옵션 |
| 반복 | 조건마다 1회(수업), 가능하면 3회 |
| 지표 | 인수 통과율, 전체 테스트, 규칙 위반, 개입, 시간, 토큰, 비용, 위험 시도, `.env` 노출 |
| 판정 기준 | 세 작업 모두에서 on의 규칙 위반이 off보다 적고 인수 통과율이 같거나 높으면 v1을 유지한다. 비용이 두 배를 넘으면 부품별로 덜어 보는 실험을 한다 |
| 통제하지 못한 것 | 사용자 범위 설정과 플러그인, 실행 시각, 모델의 비결정성 |

## 10. 유지보수

- 더하는 조건: 같은 실패가 두 번 관찰되었고, 그 실패를 막는 기존 부품이 없을 때
- 지우는 조건: 그 부품을 뺀 조건과 측정 차이가 없을 때, 또는 한 학기 동안 발화하지 않았을 때(발화하지 않은 까닭을 먼저 확인)
- 다시 측정하는 시점: 모델을 바꿀 때, Claude Code의 주 판이 바뀔 때, 부품을 셋 이상 바꿀 때
- 크기 상한: `CLAUDE.md` 60줄, 경로별 규칙 파일당 20줄, 플러그인 상시 비용 합계 200토큰
