# 배포 점검표

이 양식을 `docs/운영/배포점검표.md`로 복사해 쓴다. 1절은 배포할 때마다 그대로 따라 하는 점검 목록이고, 2절은 배포마다 한 행씩 쌓는 기록이다. 점검 항목 가운데 기계가 확인하는 것은 「자동」 칸에 그 검사의 이름을 적는다.

## 1. 점검 목록

### 1-1. 배포 전 (태그를 만들기 전)

| 번호 | 점검 | 자동 | 확인 방법 |
|---|---|---|---|
| B1 | main의 마지막 커밋에서 CI 네 검사(test, eval, secrets, rules)가 모두 통과했다 | CI | PR 화면 또는 `gh run list --branch main --limit 1` |
| B2 | 잠금 파일이 `requirements.txt`와 맞고, 해시가 모두 있다 | CI(rules) | `python ops/version/check_pins.py` |
| B3 | `.env.example`의 `LLM_MODEL`, `PROMPT_SUMMARY`, `PROMPT_ASK`가 이번 판에서 쓸 값이다 | CI(rules) | 같은 명령, 그리고 값이 의도한 것인지 사람이 본다 |
| B4 | `CHANGELOG.md`에 이번 판의 절이 있고, 판 번호가 시맨틱 버저닝의 규칙에 맞다 | 수동 | `python ops/release/notes.py --check v「X.Y.Z」` |
| B5 | 저장소와 배포물에 비밀 정보가 없다 | CI(secrets) | `python security/scan_secrets.py` |
| B6 | `web/`에 키, 개인 정보, 내부 주소가 없다. Pages 사이트는 저장소가 비공개여도 공개된다 | 수동 | `ls web`, `grep -rn "「찾을 말」" web` |
| B7 | 「」 | 「」 | 「」 |

### 1-2. 릴리스와 배포 (GitHub)

| 번호 | 점검 | 자동 | 확인 방법 |
|---|---|---|---|
| D1 | 태그를 푸시하자 `Release` 워크플로가 네 검사를 다시 돌리고 릴리스를 만들었다(API는 릴리스까지) | CI | `gh release view v「X.Y.Z」` |
| D2 | 배포할 태그의 커밋에서 CI 네 검사가 success이다 | 배포 | `bash ops/release/ci_passed.sh v「X.Y.Z」`(`pages.yml`도 같은 스크립트로 확인한다) |
| D3 | 웹을 그 태그로 배포했다 | 배포 | `gh workflow run pages.yml -f tag=v「X.Y.Z」`, `gh run watch` |
| D4 | 되돌릴 판(직전 릴리스)이 있다 | 수동 | `gh release list` |

### 1-3. 배포 뒤

| 번호 | 점검 | 자동 | 확인 방법 |
|---|---|---|---|
| A1 | Pages의 판 표시가 배포한 판과 커밋이다 | 수동 | `curl -s 「Pages 주소」version.txt` |
| A2 | 릴리스한 판의 API를 내 PC에서 띄워 주요 경로(목록, 상세, 질의응답)를 한 번씩 불렀다 | 수동 | `curl` 세 번(6-5) |
| A3 | 문제가 있으면 웹을 직전 판으로 되돌린다: `gh workflow run pages.yml -f tag=「직전 판」` | 수동 | 되돌린 뒤 A1 |
