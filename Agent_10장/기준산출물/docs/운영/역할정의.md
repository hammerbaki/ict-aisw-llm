# jobprep 운영 에이전트 시스템 역할 정의서 v0.1 (1장 견본)

> 1장 「AI 에이전트 운영의 요건」의 산출물이 없는 학습자를 위한 간단한 견본이다. 1장에서 자기 역할 정의서를 썼으면 그것을 쓴다. 10장 4절에서 이 문서를 v0.2로 고친다.

| 항목 | 내용 |
|---|---|
| 대상 | `jobprep`을 운영하는 에이전트들과 사람(운영 책임자) |
| 근거 | `docs/운영/운영요건.md` v0.1 |
| 판 | v0.1 |

## 1. 역할 요약

| ID | 역할 | 한 줄 설명 | 구현하는 장 |
|---|---|---|---|
| R1 | 기획 | 이슈를 받아 작업 계획과 인수 조건을 쓴다 | 10 |
| R2 | 구현 | 계획과 테스트에 따라 코드를 고친다 | 2, 7, 8 |
| R3 | 테스트 | 요구를 테스트로 바꾸고 실행해 판정한다 | 2, 6, 12 |
| R4 | 검토 | 변경을 규칙과 요건에 비추어 읽고 의견을 낸다 | 6, 10 |
| R5 | 배포 | 검사를 통과한 판에 태그를 붙이고 배포·되돌리기를 준비한다 | 13 |
| R6 | 관측 | 운영 기록을 읽어 요건 위반과 비용을 보고한다 | 5, 12 |
| 사람 | 운영 책임자 | 계획을 승인하고, 병합과 배포를 결정하고, 넘겨받은 실패를 처리한다 | 전 장 |

## 2. 역할

| ID | 권한 | 입력 | 출력 | 완료 조건 | 사람 승인 지점 |
|---|---|---|---|---|---|
| R1 기획 | 읽기: 저장소 전체(`.env` 제외). 쓰기: 계획 문서. 금지: 코드와 테스트 수정, 커밋 | 이슈, 명세서, 운영 요건 | 계획 문서 | 작업 단위마다 인수 조건과 판정 명령이 있다 | 계획 승인 |
| R2 구현 | 쓰기: `api/`, `rag/`, `web/`. 실행: `pytest`, 작업 브랜치에 커밋. 금지: 기존 테스트 수정, `main`에 커밋·푸시 | 승인된 계획, 실패하는 테스트 | 작업 브랜치의 커밋, 변경 요약 | `pytest -q` 통과, 기존 테스트 그대로 | 계획에 없는 파일을 고쳐야 할 때 |
| R3 테스트 | 쓰기: `tests/`의 새 파일. 실행: `pytest`. 금지: 구현 코드 수정, 동결된 테스트 수정 | 계획의 인수 조건 | 새 테스트, 판정 기록 | 새 테스트가 구현 전 실패, 구현 뒤 통과 | 테스트 동결 |
| R4 검토 | 읽기: 저장소 전체(`.env` 제외), 차이. 금지: 코드 수정, 병합 | 작업 브랜치와 `main`의 차이, 규칙 | 검토 의견 | 의견마다 근거(규칙, 요구 ID)가 있다 | 사람이 의견을 읽고 병합을 정한다 |
| R5 배포 | 실행: `git tag`, 점검 명령. 금지: 승인 없는 배포 | 병합된 `main`, CI 결과 | 태그, 배포 점검표 | 점검표 통과, 되돌릴 판 기록 | 배포, 되돌리기 |
| R6 관측 | 읽기: `logs/`. 쓰기: 관측 보고서. 금지: 코드·설정 수정 | 운영 기록 | 관측 보고서 | 요건별 측정값과 계산 명령 | 장애를 이슈로 올릴 때 |

## 3. 흐름

이슈 → R1 기획(계획) → 사람: 계획 승인 → R3 테스트(실패하는 테스트) → R2 구현 → R3 테스트(판정) → R4 검토 → 사람: 병합 → R5 배포 → 사람: 배포 실행 → R6 관측 → (위반이면 새 이슈)

## 4. 역할을 나눈 까닭

- 작성자와 검토자를 나눈다. 같은 맥락에서 자기 변경을 검토하면 같은 가정을 되풀이하기 쉽다.
- 테스트를 쓰는 역할과 구현하는 역할을 나눈다. 구현 역할이 테스트를 고쳐 통과시키는 회피를 권한으로 막는다.
- 되돌리기 어려운 일(병합, 배포)은 사람이 승인한다.
